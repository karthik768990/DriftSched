# Holdout Learning and Drift-Aware Scheduling

**Project:** DriftSched (Drift-Aware Quantum Experiment Scheduling)
**Code:** `analysis/holdout.py`, `analysis/priorities.py`, `scheduling/drift_aware.py`, `evaluation.py`, `scripts/run_holdout_evaluation.py`
**Status:** Implemented

> These are held-out replay scheduling metrics on recorded outcomes. They do not
> predict counterfactual hardware outcomes, and the observed historical outcome
> difference is not a physical comparison error. Counterfactual hardware-performance
> claims require a later drift/outcome model.

## 1. Pipeline

```text
full recorded trace
   -> chronological split (train < boundary <= holdout)
   -> windowed pairwise drift diagnostics on TRAIN only
   -> priority score for all 91 compatible pairs  -> frozen PriorityTable (+ JSON artifact)
   -> HOLDOUT shots only
   -> {arrival-order, consecutive-pair, drift-aware} on the same slots and workload
```

**Compatibility and priority are different things.** Compatibility is the researcher
decision in `data/compatibility_registry.csv`: all 91 Ramsey pairs are `compatible`, and no
drift score can change that. Priority only orders which compatible comparison to run next.

## 2. Chronological split rule

```text
boundary = min_timestamp + train_fraction * (max_timestamp - min_timestamp)
training: timestamp < boundary        holdout: timestamp >= boundary
```

Defaults: `train_fraction = 0.75`, `window_seconds = 600`. The split is purely temporal (no
random sampling, no per-circuit index) and keeps input order inside each partition. It
rejects fractions outside `(0, 1)` and non-positive windows, empty or zero-span traces,
duplicate shot ids, and any circuit with fewer than 10 training or 2 holdout shots.

On `data/dataset.txt` the boundary is `21920.355064249998 s`: 63,041 training shots in
`[0.120257, 21919.8]` and 20,959 holdout shots in `[21921.7, 29227.1]`.

## 3. Anti-leakage guarantee

- `learn_pair_priorities` receives only the training partition and raises `LeakageError`
  if any shot has `arrival_time >= boundary`.
- It never receives holdout outcomes, so they cannot influence a score. Tests flip every
  holdout outcome (on synthetic data and on the full dataset) and require a byte-identical
  priority table; they also check that changing a training outcome does change it.
- The table records a SHA-256 fingerprint of the training shots it used.
- The priority table is immutable and is frozen before any holdout simulation starts.
- The holdout workload uses only holdout shots. The round alignment of the workload comes
  from per-circuit shot order in the full trace (no outcomes, no priorities); a request is
  created only when both of its shots are in the holdout, so training shots never run in
  the replay. A few straddling-round shots may have no request (reported as
  `unrequested_shots`).

## 4. Priority learning

Training shots are grouped per circuit and windowed with the existing, validated
`compute_windowed_stats` (windows aligned to the trace minimum, covering `[origin, boundary)`)
and `analyze_pairwise_drift` (default 5 shots per window cell). For each compatible registry
pair the record stores valid and unusable transition counts, `mean_abs_d`, `rms_d`,
`mean_abs_z`, a sufficiency flag, the score and a rank. The exact score is:

```python
priority_score = 1.0 / (mean_abs_z + 1e-12)       # lower training mean|Z|  ->  higher priority
```

**Zero-score fallback:** a pair with fewer than `min_valid_transitions` (default 10) valid
training transitions, or a non-finite `mean_abs_z`, gets `priority_score = 0.0`. It stays
`compatible` and can still be scheduled when no positively scored request is ready. No
threshold such as `mean_abs_z <= 1.96` is used, and no physical Ramsey/T2* model is fitted.
Ranks sort by score descending, then wait lengths.

The artifact (default `data/derived/pair_priorities.json`, git-ignored, regenerated by the
CLI) holds the metadata (fractions, window, boundary, origin, fingerprint, formula) and one
record per pair.

## 5. Drift-aware dispatch rule

`DriftAwarePairPolicy` uses the same atomic two-slot block semantics as
`consecutive-pair`: only ready, compatible requests whose two shots have arrived and are
unexecuted are candidates; the one with the highest score is dispatched; the smaller-`k`
circuit runs first and the other runs in the immediately following slot with nothing in
between; with no ready request the slot idles (strict idling). It maps to the sort key
`(-score, request_order_key(request))`, so zero-score requests are chosen only when no
positive-score request is ready, using the same tie-breakers. It only reads an immutable
lookup, so it cannot mutate priorities, read holdout diagnostics, reuse shots or bypass the
registry (the simulator validates every request).

## 6. Tie-breaking

Equal scores fall through, in order, to: earlier pair-request arrival time (the later of the
two shots' arrivals), lower sorted wait-length tuple `(min k, max k)`, earlier source indices,
then the stable request id.

## 7. Fairness conditions

All three policies receive identical holdout source shots, the same logical slot budget
(default one slot per holdout shot), the identical prebuilt request workload, the same
registry and, for drift-aware, one frozen training-derived priority table. `run_holdout_evaluation`
checks that the budgets and workloads match.

## 8. Limitations

- Because the workload is a fixed, policy-independent set of comparisons and the slot budget
  is about one slot per shot, the pair policies mainly differ in dispatch order. When the
  queue holds few ready requests, `consecutive-pair` and `drift-aware` behave almost
  identically; drift-aware can also leave low-priority requests waiting longer.
- Observed outcomes are replayed as recorded. Running two shots back to back in this replay
  does not change what was measured, so metrics such as the observed outcome difference do
  not show a benefit of closeness. Only slot separation, time separation, waiting, idle slots
  and completion are scheduling quantities here.
- The default slot budget, the round-robin workload and `min_valid_transitions = 10` are
  documented modelling choices, adjustable from the CLI where applicable.
- A later phase needs a drift/outcome model before any claim about comparison error,
  uncertainty or hardware performance under a reordered schedule.
